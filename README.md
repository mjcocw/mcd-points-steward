## 💡 它解决什么问题

每个人账户里都躺着麦当劳积分，但几乎没人真的算过账：

- 账户里有一批积分**下个月就作废**，你没收到任何提醒
- 麦麦省的券躺在卡包里，**没人领、没人用**
- 商城里 1 积分到底能换几毛钱？抽一次奖**期望值是多少**？是不是纯玄学？

**McPoints Steward** 把这些一次性算清楚，输出一张**能直接截图发群**的资产体检报告。

一句话：**它不是帮你省钱的工具，是帮你把积分真正花出去的会计。**

## 🧨 我对接真实接口时踩到的五个坑

这个项目最有价值的部分不是代码，是**把麦当劳官方 MCP 的真实行为摸清楚了**。
以下每一条都是实测出来的，不是猜的：

| # | 坑 | 真实表现 | 本项目的处理 |
|---|---|---|---|
| 1 | **价格藏在名字里** | `mall-points-products` 的 `price` 字段对商品券**恒为 0**，真实面值在 `spuName` 里（`"21.9元巨无霸可乐组合"`） | 从名称反推面值，失败则标为「无法估值」而不是编一个数 |
| 2 | **一半商品已下架** | 实测 50 件商品里 43 件不可用：`downTime` 已过（有些 3 月就结束了）、或 `point=0` 的派对/读书会等体验类 | 按 `downTime` 过滤 + 排除非积分兑换物，**绝不让用户去兑换已经下架的东西** |
| 3 | **抽奖不公布概率** | `query-lottery-info` 只给奖品名单，**既没有中奖概率，也没有面值** | 按等概率假设计算，并在报告里**明确标注这是上界、会高估**，同时给出方差与「颗粒无收概率未知」 |
| 4 | **官方把 Month 拼成了 Mouth** | 账户字段是 `currentMouthExpirePoint` / `nextMouthExpirePoint` | 别名表同时收两种拼写，字段改名不会崩 |
| 5 | **业务错误不抛异常** | 参数错时返回 `{"success": false, "code": 600050, "message": "收藏餐厅列表为空…"}`，HTTP 200 | 专门的 `business_error()` 识别，把错误写进报告而不是当成"查到了但没数据" |

**外加一个纯工程坑**：`urllib` 每次请求都新建 TLS 握手，在企业代理 / WAF 环境下会被中间设备掐断
（`SSLEOFError`）。所以客户端改成了**持久化 keep-alive 连接 + 自动重连重试**，
并支持 `https_proxy` 环境变量的 CONNECT 隧道 —— 国内公司网络几乎都要走这一步。

## 🎯 三个别人不会算的东西

### ① 个人边际效用折扣 —— 同一张券，对不同人价值不同

券上写「5 元」，但如果你本来就会花这 5 元买可乐，这张券对你的真实价值远不止 5 元；
反过来，一张 50 元的周边你可能压根不想要。

所以每张券、每个奖品、每件商品都会乘一个**效用系数**：

| 对象 | 效用系数 | 理由 |
|---|---|---|
| 巨无霸 | 1.00 | 招牌，而且本来就是你会买的东西 |
| 中可乐 | 0.25 | 你本来就会买可乐，这张券只是省了决策 |
| 5 元代金券 | 0.85 | 通用、立刻能抵扣 |
| 麦乐鸡（5 块） | 0.65 | 要真去吃才有价值 |
| 麦麦帆布袋 | 0.35 | 实物，喜好差异极大 |
| 谢谢参与 | 0.00 | 没有价值 |

还专门处理了一个真实坑：**「16.9元麦辣可乐组合」不能按"可乐 0.25"计价** ——
那是汉堡+一杯可乐的整份套餐，按饮料系数算会把整份价值砍掉四分之三。
所以组合名里的饮料词条会被跳过，改用主料和品类系数。

**不建模这一层，所有"积分价值"的结论都是错的。**

### ② 抽奖期望值 + 方差 + 颗粒无收概率

从 `query-lottery-info` 拉下奖品池，逐项解析面值、折算效用价值、求期望与标准差：

```
单次期望 8.38 元   标准差 8.64 元   颗粒无收概率 未知（官方未公布概率）
每积分期望 0.3491 元  ←  是兑换汇率 (0.0338 元/分) 的 10.3 倍
```

标准差和期望值几乎一样大 —— 说明抽奖是**高方差**选项。
工具不会只给你一句"快去抽"，而是把**期望值和最差情况并排摆出来**让你自己选。

而"等概率假设会高估期望值"这句话，会原封不动出现在报告里。

### ③ 三条路线量化对比 + 0/1 背包求解

不告诉你"应该怎样"，而是把三种花法都算到小数点后一位：

```
路线                    期望值      最差情况      积分用掉
稳健型：全部换成确定的商品      152.4元    152.4元    1,200分
平衡型：到期积分抽奖，长期积分兑换  229.7元    145.9元    1,240分 ←推荐
进攻型：积分全部拿去抽奖       544.7元    117.4元    1,224分
```

兑换商品的选择用 **0/1 背包**精确求解（积分离散化 + DP + 回溯），保证在积分上限内效用价值最大。

**最终推荐逻辑是可解释的**，不是拍脑袋：

> 你有 240 积分将在 30 天内过期，机会成本为零 —— 抽奖的每积分期望值（0.3491 元）
> 是兑换汇率（0.0338 元）的 10.3 倍，所以**「到期就抽、长期就换」**是期望值最高且风险可控的组合。

## 🚀 快速开始

### 三行命令跑起来（**不需要任何 Token**）

```bash
git clone https://github.com/mjcocw/mcd-points-steward.git
cd mcd-points-steward
python main.py --mock --html demo/report.html
```

零第三方依赖，Python 3.9+ 开箱即用。`--mock` 的数据**字段结构与真实接口完全一致**
（含 `spuName` / `point` / `downTime` / `currentMouthExpirePoint` / `drawPoint`），
所以 **mock 下跑通 = 真实接口下也能跑通**。

### 跑你自己的真实账户

**第 1 步**：到 [麦当劳 MCP 开放平台](https://open.mcd.cn/mcp) 用手机号登录 → 控制台 → 激活，申请 MCP Token。

**第 2 步**：在 WorkBuddy 里配置自定义连接器（左侧边栏 → 专家·技能·连接器 → 自定义连接器 → 配置 MCP）：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": {
        "Authorization": "Bearer YOUR_MCP_TOKEN"
      }
    }
  }
}
```

> ⚠️ 记得把 `YOUR_MCP_TOKEN` 换成真实 Token。

**第 3 步**：跑起来

```bash
export MCD_MCP_TOKEN=你的Token       # Windows: set MCD_MCP_TOKEN=你的Token
python main.py --live --city 上海 --html my-report.html
```

> `--city` 用于解析门店菜单价（真实接口的 `query-meals` 强制要求 `storeCode`）。
> 不传也能跑，只是券的估值会退回到内置参考价表。

### 其他用法

```bash
python main.py --mock --json result.json   # 导出结构化结果，方便二次开发
python main.py --live --horizon 60          # 把到期高危窗口放宽到 60 天
python selftest.py                          # 40 项自检，验证核心计算链路
```

## 🔌 用到的麦当劳 MCP 能力

| Tool | 用途 | 在本项目中的角色 |
|---|---|---|
| `query-my-account` | 积分账户总览：可用 / 累计 / 冻结 / 已过期 / 即将过期 | 资产盘点 + 到期预警的数据源 |
| `query-my-coupons` | 卡包中已持有的优惠券 | 计算零成本收益，识别最先失效的券 |
| `available-coupons` | 麦麦省当前可领但未领的券 | 找出"0 成本白拿"的部分 |
| `mall-points-products` | 麦麦商城积分兑换商品清单 | 反推积分汇率 + 背包求解的物品池 |
| `query-lottery-info` | 积分抽奖活动：奖品池、消耗积分、是否可参与 | 期望值 / 方差 / 颗粒无收概率 |
| `query-nearby-stores` | 解析门店编码（`searchType=2` 需 city + keyword） | 为菜单查询铺路 |
| `query-meals` | 门店在售菜单与价格 | 给"免费券"估算真实面值 |
| `query-store-coupons` | 该门店实际可用的券 | 补充"我这店能用哪些券" |

服务端当前共开放 **35 个 Tool**；本项目只用了 8 个只读接口，
**不下单、不付款、不领券**（`auto-bind-coupons` 刻意未接入）。

调用流程、字段映射、降级策略详见 [`MCP_INTEGRATION.md`](./MCP_INTEGRATION.md)。

## 🧮 计算原理

```
   query-my-account ──▶ 可用积分 / 已过期 / 即将过期积分池
                                │
 query-my-coupons ──┐           │
 available-coupons ─┼──▶ 券面值解析（券名正则 + 菜单价匹配）
                    │           │
 mall-points-products┼──▶ 积分汇率（在架商品「面值÷积分价」中位数）
                    │     + 背包求解物品池
 query-lottery-info ┼──▶ 期望值 / 方差 / 颗粒无收概率
                    │           │
 query-meals ───────┘           ▼
        │            ┌────────────────────────┐
        └───────────▶│  个人边际效用折扣模型     │  ← 本项目的核心
                     │  价值 = 面值 × 效用系数   │
                     └───────────┬────────────┘
                                 ▼
              ┌──────────────────┼──────────────────┐
              ▼                  ▼                  ▼
          稳健型              平衡型              进攻型
        全部兑换           到期抽+长期换        全部抽奖
        (0/1背包)          (期望值最高)        (高方差)
              └──────────────────┼──────────────────┘
                                 ▼
                    期望值 / 最差情况 / 颗粒无收概率
                                 ▼
                     终端报告 + 单文件 HTML 报告
```

**关键取舍**：所有估值都乘了效用系数，所以报告里的"元"是**对你而言的价值**，不是标价。
这也是为什么同一套数据，工具会给出"中可乐只值 2.5 元"这种反直觉但正确的结论。

## 🛡️ 设计边界（诚实声明）

这个项目**不做什么**，和它**做什么**一样重要：

- **不下单、不付款、不领券、不动你的账户**。全程只读，唯一会写的是你手动点「一键领券」那一下。
- **不处理你的个人身份数据**。MCP Token 只从环境变量读取，绝不写进代码或配置文件。
- **所有估值是估算，不是官方口径**。面额来自接口返回值与公开菜单价，效用系数是本项目公开的
  启发式参数，你可以按自己的偏好改 `valuation.py` 里的 `NAME_UTILITY` 和 `REFERENCE_PRICES`。
- **抽奖期望值是上界**。官方不公布中奖概率，等概率假设会高估 —— 这一点在报告里写明了。
- **不构成任何消费建议**。餐品信息、价格与供应状态以麦当劳官方渠道实时结果为准。
- **接口字段名会变**。所有解析都走多候选键名 + 别名表，字段改名不会让项目崩掉；
  解析不出来的项会被计数并写进报告，而不是被静默吞掉。
