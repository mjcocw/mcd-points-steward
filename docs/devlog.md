## 一、事情的起点：一句话把我戳中了

我给自己的麦当劳账号写了个小工具，跑完第一遍，它告诉我：

```
【到期预警】
  ✖ 积分    143 份  已经过期   约值 7.8 元   —— 无法挽回
【说明】
  · 商城共 50 件商品，43 件因下架/非积分兑换/缺面值被排除，实际参与汇率计算的样本 7 件
  · 当前账户无法参与抽奖：积分不足
```

**我的 143 积分早就过期了。** 不是"快过期"，是**已经**过期 —— 我完全不知道。

麦当劳的积分规则是"每 12 个月清零"，但系统不会提醒你。而我翻了翻自己的账户，**还有 3 张麦麦省券（共 35 元）躺在里面没领**。

那一刻我就决定：这事儿该有人干，而且应该是个工具，不该靠人肉翻。

于是有了 **麦麦积分资产管家（McPoints Steward）**。

## 二、为什么选「积分资产」这个赛道

先说下背景：这是 1024 程序员节的一个比赛，用**麦当劳官方 MCP Server** 开发 Skill，**排名完全看 GitHub Star 数**。

我 10 月 22 日抓了当时的完整榜单：**104 个项目**，其中：

| 赛道 | 项目数 |
|---|---|
| 省钱 / 优惠券 | ~20 |
| 趣味 / 人格 / 玄学 | ~13 |
| 点餐 / 全能助手 | ~11 |
| 派对 / 活动日历 | ~8 |
| 开发者梗 | ~8 |
| 营养 / 卡路里 | ~7 |
| **积分 / 商城 / 抽奖** | **4** |
| **团餐 / 企业订餐** | **2** |

再对照麦当劳 MCP 开放的 30 多个 Tool，有**三整条链路几乎没人碰**：

- `query-my-account` —— 它的返回里有一个字段叫 **`currentMouthExpirePoint`（本月底到期积分）**。这个字段就是整个项目的起点。
- `mall-points-products` —— 麦麦商城积分兑换商品，**实测 50 件里 43 件不可用**（下架了 / 不是积分兑换物）。
- `query-lottery-info` —— 积分抽奖活动，奖品池完整公开，但**从不告诉你中奖概率**。

**官方开放了能力，榜单上却没人用。** 这就是空位。

## 三、六个坑（这部分是干货，接真接口才会遇到）

我一开始是照着文档猜字段名写解析层的。接上真 Token 一跑，**几乎全错**。以下是实测结论：

### 坑 1：价格藏在名字里，`price` 字段恒为 0

`mall-points-products` 返回的商品长这样：

```json
{ "spuName": "21.9元巨无霸可乐组合", "point": "800", "price": "0", ... }
```

`price` 是 **0**。真实面值在 `spuName` 里。

如果你按常规写法取 `price` 字段去算"1 积分值多少钱"，算出来的是**除以无穷大**。

**处理**：从名称解析面值（`/(\d+(?:\.\d+)?)\s*元/`），失败就标"无法估值"，绝不编一个数。

### 坑 2：一半商品已经下架了

实测 50 件商品：

```
catName 分布: 到店专用 21, 主题类派对 13, 品鉴会 7, 生日类派对 6, 读书会 1, 玩具 1, 鞋袜 1
其中 point > 0 的有 23 件
```

而这 23 件里，`downTime` 早于今天的有一大半（有些是 3 月 21 日就结束了）。

**不过滤的后果**：工具会兴高采烈地推荐你"用 800 积分兑换 18.8元板烧鸡腿堡两件套" —— 而那个券 7 个月前就下架了。

**处理**：按 `downTime` 过滤 + 排除 `point=0` 的派对/读书会等体验类。实测 **50 → 7 件**。

### 坑 3：抽奖不公布概率，也不公布面值

`query-lottery-info` 的奖品只有三个字段：

```json
{ "name": "麦辣三件套5折券", "typeText": "优惠券", "imageUrl": "https://..." }
```

**没有 probability，没有 value。**

这意味着"抽奖值不值"这个问题，**你只能自己建模**。如果按等概率假设，期望值会算得很好看 —— 但真实抽奖里大奖必然更稀有，**等概率假设是上界，不是期望**。

**处理**：
- 面值从奖品名解析（`"下单立减3元券"` → 3 元；`"麦辣三件套5折券"` → 麦辣单价 × 3 × 5 折；`"30积分"` → 30 × 积分汇率）
- 概率按等概率假设，但**在报告里明写**「官方未公布概率，按等概率假设（结果偏乐观）」，并把「颗粒无收概率」显示为 **"未知"** 而不是 0%

### 坑 4：官方把 Month 拼成了 Mouth

```json
{ "currentMouthExpirePoint": "0", "nextMouthExpirePoint": "0", "lastMouthExpirePoint": "0" }
```

**M-o-u-t-h**。不是笔误式的小事 —— 你的正则写 `currentMonthExpirePoint` 就永远匹配不上。

**处理**：别名表同时收两种拼写。（顺便，官方返回的数值是**字符串**且带小数：`"143.3"`）

### 坑 5：业务错误不抛异常，返回 HTTP 200

参数传错时，官方不会给你 4xx，而是：

```json
{ "success": false, "code": 600050, "message": "收藏餐厅列表为空，请您提供城市+关键词进行搜索" }
```

**HTTP 200 + success:false**。你要是当普通数据解析，就会得到"接口正常返回但列表是空的" —— 然后静默丢掉一条重要信息。

**处理**：专门的 `business_error()` 识别这种结构，把 `[600050] 收藏餐厅列表为空…` 写进报告的说明区。

### 坑 6：`query-meals` 强制要门店，而门店搜索的参数有隐藏约定

菜单接口要 `storeCode`，得先查门店。而 `query-nearby-stores` 的参数约定是：

| `searchType` | 含义 | 实测 |
|---|---|---|
| `1` | 查收藏餐厅 | 没收藏 → `600050` 收藏餐厅列表为空 |
| `2` | 按位置搜 | **必须同时给 `city` 和 `keyword`**，否则 → `600058` 城市名或者关键词不能为空 |

**处理**：依次尝试"查收藏 → 按城市搜"，全失败才在报告里提示；并把城市暴露成 CLI 参数 `--city`。

### 附带一个纯工程坑：企业代理会把 TLS 握手掐断

`urllib` 每次请求都新建 TLS 连接，在公司代理 / WAF 环境下会**间歇性** `SSLEOFError`。我一度以为是代码 bug，查下来是中间设备对高频新建连接的限制。

**处理**：改用 `http.client.HTTPSConnection` **保持 keep-alive**，单次会话只握手一次；并支持 `https_proxy` 的 CONNECT 隧道 + 断线自动重连重试。

这条对国内企业用户是刚需，我把它写进了 README 的卖点。

## 四、三个方法论：让它不只是"算个数"

光算数字没用，得算得**有意义**。三个核心设计：

### ① 个人边际效用折扣

券上写「5 元」，但如果你本来就会花这 5 元买可乐，这张券对你的真实价值远不止 5 元；反过来一张 50 元的周边你可能压根不想要。

所以每张券、每个奖品都乘一个效用系数：

```
巨无霸 1.00 | 麦辣鸡腿堡 0.90 | 中可乐 0.25 | 5元代金券 0.85
麦乐鸡 0.65 | 麦麦帆布袋 0.35 | 谢谢参与 0.00
```

还专门处理了一个真实坑：**「16.9元麦辣可乐组合」不能按"可乐 0.25"计价** —— 那是汉堡 + 一杯可乐的整份套餐，按饮料系数算会把整份价值砍掉四分之三。所以组合名里的饮料词条会被跳过，改用主料和品类系数。

**不建模这一层，所有"积分价值"的结论都是错的。**

### ② 抽奖：期望值 + 方差 + 颗粒无收概率

```
单次期望 8.38 元   标准差 8.64 元   颗粒无收概率 未知（官方未公布概率）
每积分期望 0.3491 元  ←  是兑换汇率 (0.0338 元/分) 的 10.3 倍
```

**标准差和期望值几乎一样大** —— 这是个高方差游戏。工具不给你一句"快去抽"，而是把期望值和最差情况并排摆出来。

### ③ 三条路线量化对比 + 0/1 背包

不告诉你"应该怎样"，而是把三种花法都算到小数点后一位：

```
路线                    期望值      最差情况      积分用掉
稳健型：全部换成确定的商品      152.4元    152.4元    1,200分
平衡型：到期积分抽奖，长期积分兑换  229.7元    145.9元    1,240分 ←推荐
进攻型：积分全部拿去抽奖       544.7元    117.4元    1,224分
```

兑换商品的选择用 **0/1 背包**精确求解（积分离散化 + DP + 回溯），保证在积分上限内效用价值最大。

**推荐理由是可解释的，不是拍脑袋**：

> 你有 240 积分将在 30 天内过期，机会成本为零 —— 抽奖的每积分期望值（0.3491 元）是兑换汇率（0.0338 元）的 10.3 倍，所以「**到期就抽、长期就换**」是期望值最高且风险可控的组合。

## 六、怎么跑

**不需要任何 Token**（评审者 clone 下来 10 秒就能看到完整效果）：

```bash
git clone https://github.com/mojc/mcd-points-steward.git
cd mcd-points-steward
python main.py --mock --html demo/report.html
```

`--mock` 的数据**字段结构与真实接口完全一致**（含 `spuName` / `point` / `downTime` / `currentMouthExpirePoint` / `drawPoint`），所以 **mock 下跑通 = 真实接口下跑通**。

跑自己的账户：

```bash
export MCD_MCP_TOKEN=你的Token
python main.py --live --city 上海 --html my-report.html
```

**零第三方依赖**，Python 3.9+ 开箱即用。`python selftest.py` 有 40 项自检覆盖全部计算链路。

## 七、边界（我做了什么、没做什么）

- **不下单、不付款、不领券、不动你的账户**。全程只读。`auto-bind-coupons`、`create-order`、`draw-lottery` 这些写接口**刻意没有接入**。
- **不处理个人身份数据**。Token 只从环境变量读，不进仓库。
- **抽奖期望值是上界**，因为官方不公布概率 —— 这一点在报告里写明了。
- **所有估值是估算**，效用系数和参考价表都是公开的启发式参数，你可以按自己偏好改。
- **接口字段名会变**。所有解析走多候选键名 + 别名表，字段改名不会让项目崩；解析不出来的项会写进报告，而不是被静默吞掉。
